# 架构说明

## 为什么是「逻辑多角色、物理单中枢」

立项时评估过两条路：

| 方案 | 结论 |
|---|---|
| 多 Agent 集群（每个职能一个独立服务） | ❌ 一个人/小团队养不起：部署面大、调试链长、Token 成本翻倍 |
| **单中枢 + prompt 模块分角色** | ✅ 选这条：一个中枢函数内按「情感分析→经营决策→营销分层→文案生成」串行调用，逻辑上是四个角色，物理上是一个函数 |

对评委/对用户的说法：**四个 Agent 角色真实存在，只是共享一个运行体**——这是成本约束下的工程取舍，不是能力缺失。跑通后任意角色可拆出去独立部署，接口不变。

## 数据流（每日闭环）

```
顾客评价/领券 ──► 云数据库(reviews/coupons/users)
                        │
              20:30 定时触发 review-analyzer
                        │
        ① 读当日评价（无评价则读近7天，标记数据窗口）
        ② LLM 情感分析：好评率/关键词/典型差评
        ③ 场景四分法决策（只选一个，防轰炸）：
           好评≥70%      → 好评裂变（推好友券方案）
           差评关键词命中 → 差评安抚（推道歉券方案+整改建议）
           沉睡用户占比高  → 沉睡召回（推唤醒券方案）
           以上都不显著    → 菜品优化（基于口味关键词给建议）
        ④ 生成一条「明日建议」写入 agentLog（status: pending）
                        │
        老板看板打开 → 看到建议 → 点「照办」
                        │
              retention-pilot（审批闸门）
        ⑤ 校验参数 → 落券到 coupons 集合 → 标记 agentLog: applied
        ⑥ 次日核销/分享数据回流，形成复盘输入
```

## 关键设计决策

1. **审批闸门不可绕过**：所有「动钱」动作（发券、改面额）必须老板点击确认，AI 只生成方案。函数级实现，不靠前端自觉。
2. **AI 输出留痕**：每次中枢运行写一条 agentLog（输入摘要/决策场景/输出方案/Token 用量），可审计、可复盘、可向监管说明。
3. **数据最小化**：只存 openid（微信侧匿名标识）+ 评价文本 + 券状态；不收集姓名、手机号、位置。合规不是附加功能，是卖点。
4. **知识增强而非通用生成**：文案函数强制注入本店真实好评（loadPraiseQuotes）+ 行业知识包（kb 集合），从机制上防止「AI 味模板文案」。
5. **保险丝**：llmUsage 集合记录每次 Token 消耗，月度超阈值自动降级为模板文案，防止成本失控。

## 技术栈

- 微信云开发（云函数 Node.js + 云数据库 + 定时触发器）—— 个体户零服务器运维
- LLM：任何兼容 OpenAI Chat Completions 的接口（环境变量切换，不锁死供应商）
- 无向量数据库：行业知识用「规则化知识包」（kb 集合按行业+场景查询），小数据量场景比 RAG 更稳、更省
