# 金字招牌 · 本地中小商家营销闭环 Agent

> 一套跑在微信云开发上的开源模板：让一家小店用 **3 张桌贴码 + 1 个 AI 经营参谋**，把「评价 → 复购 → 好友券」转起来。

适用于：餐饮、花店、茶饮、汽修、美业等**有实体门店、靠回头客赚钱**的本地小商家。

## 它解决什么问题

小老板的现实：公域平台抽佣高、评价沉在别家平台、自己没精力做营销。
这套模板做的事：

1. **顾客扫码** → 评价/领好友券（沉淀在商家自己的库里）
2. **每天 20:30** → 经营参谋自动跑：**先复盘昨日策略效果**（券核销率、差评顾客动向）→ 读当天评价 → 情感分析 → 输出一条「明日建议」（好评裂变 / 差评安抚 / 沉睡召回 / 菜品优化，四选一，只推一条，不轰炸）
3. **老板一键「照办」** → AI 生成的券方案才真正生效（动钱的动作必须人工审批，这是设计原则）
4. **知识增强文案** → 基于本店真实好评生成小红书/抖音/朋友圈/点评文案，不套通用模板

## 架构（五层）

```
┌─ 交互层    顾客端小程序 / 商家看板 / 桌贴渠道码
├─ 编排层    定时触发(20:30) + 场景四分法(好评/差评/沉睡/菜品)
├─ 中枢层    单中枢多角色：情感分析·经营决策·营销分层·知识增强文案
│            （逻辑多角色，物理单 Agent，小团队养得起）
├─ 工具层    本仓库开源的三个组件 ↓
└─ 数据层    门店私有库(评价/券/核销) + 规则化行业知识包(kb 集合)
```

合规设计：**不爬外部平台数据、不生成假点评、不收姓名手机号**（数据最小化）；发券动钱必须老板审批；AI 输出留痕（agentLog 集合）可审计。

## 快速开始（约 30 分钟）

前置：微信小程序账号 + 开通云开发 + 一个 LLM API Key（兼容 OpenAI 格式即可）。

1. 把 `agents/`、`components/` 三个目录各自作为云函数上传部署
2. 云数据库建 3 个集合：`agentLog`、`llmUsage`、`kb`
3. 运行一次 `examples/seedKb.js`（云端测试）灌入行业知识包
4. 给中枢函数配 3 个环境变量：`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`，超时改 60 秒
5. 给 review-analyzer 配定时触发器：每天 20:30
6. 按 `docs/换皮指南.md` 改成你的行业

## 组件导航

| 目录 | 作用 | 怎么搬走复用 |
|---|---|---|
| `agents/review-analyzer` | 每日经营参谋：读评价→情感分析→输出一条建议 | 改 prompt 里的行业词即可 |
| `agents/retention-pilot` | 审批闸门：老板「照办」后落券/召回，写 agentLog | 通用，任何「AI 建议+人工审批」场景可用 |
| `agents/effect-review` | 效果复盘：Agent 自我验证昨日策略（核销率+差评动向），建议滚动迭代 | 纯规则零成本，任何运营 Agent 可挂 |
| `agents/reservation-perceive` | 预约感知：桌数/点菜榜/爽约自主读取，规则化备菜提醒 | 预约制业态通用（餐饮/美业/诊所） |
| `components/ai-copywriter` | 知识增强文案：读本店好评写四平台文案 | 换知识包内容即换行业 |
| `examples/seedKb.js` | 规则化行业知识包种子脚本 | 照格式补你的行业经验 |

详细复用步骤见各目录内 README。

## 我们不做什么（边界）

- 不做泛问答机器人、不做点评代写（诱导虚假评价违规）
- 不承诺营收数字；模板只保证「流程转得起来、数据留在商家手里」
